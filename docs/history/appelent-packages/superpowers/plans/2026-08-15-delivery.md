# Delivery Skill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a portable `delivery` plugin skill that coordinates Matt Pocock ticket workflows with Orca terminals and worktrees across Claude Code and Codex.

**Architecture:** `skills/delivery/SKILL.md` is the strict, explicit-mode entry point. It loads one of three focused references for orchestration, execution, or dispatch semantics, so the common contract stays short while the selected workflow remains precise. The catalog registers `delivery` as a non-feature workflow skill and releases it with a matching patch version bump in both plugin manifests.

**Tech Stack:** Markdown skill files; Orca CLI and orchestration runtime; Matt Pocock companion skills; Node.js catalog tests; pnpm validation.

## Global Constraints

- The entry point accepts only `orchestrate`, `execute`, and `finish`; it never infers a mode from prose.
- Matt Pocock skills remain the only authority for ticket storage, readiness, dependency maps, follow-up creation, and ticket updates.
- WIP defaults to `4` and counts only active dispatches created by the current delivery run; manual terminals are unmanaged.
- Before dispatch, show and obtain approval for the ticket, work kind, provider/tier, redacted startup command, workspace, WIP, dependency rationale, and quota warning.
- Use generic `lightweight`, `standard`, and `frontier` capability tiers; `--agent auto|codex|claude` and optional verbatim `--agent-args <args>` control startup.
- Best-effort quota checks warn on an unknown result; they never claim available capacity or block dispatch solely because capacity is unknown.
- Decision, grilling, triage, and Wayfinder-child work uses a fresh active-worktree terminal. Prototype and coding work uses a child worktree unless shared uncommitted state makes that unsafe.
- No automatic worker polling or wake-ups occur after the coordinator returns. Explicit status/orchestration requests read internal Orca state and propose the next ready wave.
- Every response ends with the compact status table defined in the design.
- `finish` requires `--local-merge`, `--open-pr`, or `--close-only`; a worker report alone never authorizes ticket closure, merging, or PR creation.
- Startup arguments are never invented or modified. Redact credential-like values in all output and prompts.
- Every new `SKILL.md` must reference `../appelent-feature/references/self-improvement.md`.
- This is one atomic plugin release: all skill changes, catalog registration, documentation, and both `0.1.10` manifest bumps land in a single commit.

### Task 2: Author the portable delivery entry point and focused workflow references

**Files:**

- [ ] **Step 1: Create `SKILL.md` with frontmatter and explicit parser**

Use this frontmatter and opening contract:

```md
---
name: delivery
description: Coordinate or execute ticket work with Matt Pocock workflows and Orca terminals/worktrees. Use when the user explicitly invokes `delivery orchestrate`, `delivery execute`, or `delivery finish`.
---

# Delivery

Accept only these explicit commands:

- `delivery orchestrate <tickets-or-map> [--wip N] [--agent auto|codex|claude] [--agent-args <args>]`
- `delivery execute <ticket> [--in-place] [--agent auto|codex|claude] [--agent-args <args>]`
- `delivery finish <ticket> --local-merge|--open-pr|--close-only`

For any other invocation, print the three commands above and ask the user to choose one. Do not infer a mode.
```

Add shared rules that require the applicable Matt Pocock workflow before ticket actions, require the `orca-cli` live guide before Orca actions, define the default WIP of four, classify manual terminals as unmanaged, state that every response ends with a table, and link the selected mode to its one reference. Add a `## Self-improvement` section that points to `../appelent-feature/references/self-improvement.md`.

- [ ] **Step 2: Write `dispatch-contract.md`**

Give the reference these required headings and behavior:

```md
# Dispatch contract

## Preconditions
## Provider and tier selection
## Quota preflight
## Startup arguments
## Dispatch proposal and approval
## Orca worker creation
## Reporting and terminal ownership
```

Under **Provider and tier selection**, define `auto`, `codex`, and `claude`, and the `lightweight`, `standard`, and `frontier` tiers. Under **Quota preflight**, state that unsupported quota inspection produces `Quota: unknown — dispatch proceeds with warning`. Under **Startup arguments**, preserve `--agent-args` verbatim, show the redacted final command, use Orca's `worker-start --model/--effort` when expressible, and otherwise use its documented custom `terminal create` plus readiness and tracked-task injection route. Under **Dispatch proposal and approval**, require approval before a worker starts. Under **Reporting and terminal ownership**, require `worker_done` for supervised workers and retain a terminal only when its ticket requests a live environment.

- [ ] **Step 3: Write `orchestration.md`**

Give the reference these required headings and table:

```md
# Orchestration

## Build the ticket graph
## Classify ready work
## Propose a dispatch wave
## Dispatch and retain state
## Explicit status checks
```

Include this classification table:

| Work kind | Workflow | Workspace |
| --- | --- | --- |
| Decision | Grilling or decision workflow | Fresh terminal in the active worktree |
| Triage / Wayfinding | Triage or Wayfinder | Fresh terminal in the active worktree |
| Prototype | Prototype execution | Child worktree |
| Coding implementation | Implementation workflow | Child worktree |

Require Matt Pocock triage/Wayfinder to provide ticket storage, readiness, and dependency relations. Instruct the coordinator to create/bind an Orca Run and internal tasks, dispatch only dependency-ready work, count only its active dispatches toward WIP, and never poll after returning. `delivery orchestrate status` and later orchestration requests may read Orca task/dispatch state, surface blockers/questions, and propose a further wave. End with the exact three-column status-table schema: `Ticket | Description | Status`.

- [ ] **Step 4: Write `ticket-execution.md`**

Give the reference these required headings and table:

```md
# Ticket execution

## Readiness and optional adoption
## Work-kind routing
## Direct-execution preflight
## Execute and report
## Follow-up tickets
```

Include this routing table:

| Ready work kind | Workflow | Workspace |
| --- | --- | --- |
| Decision | Decision workflow | Fresh terminal in the active worktree |
| Grilling | Matt Pocock grilling | Fresh terminal in the active worktree |
| Wayfinder child | Matt Pocock Wayfinder | Fresh terminal in the active worktree |
| Prototype | Prototype workflow | Child worktree |
| Coding implementation | Matt Pocock implementation | Child worktree |

Specify that unready tickets offer a separate triage/Wayfinder terminal rather than plan mode. An existing `delivery execute <ticket>` terminal may offer opt-in adoption into its matching active run; no other terminal can be adopted. Direct execution outside a ticket worker shows its preflight and defaults to a child worktree; only `--in-place` permits edits in the current workspace. Report evidence/validation, blockers, and smells; offer but never silently create follow-up tickets. Retain a successful terminal, worktree, and any running development process for manual inspection.

- [ ] **Step 5: Add `finish` behavior to `SKILL.md`**

Require the named completion flag, validate reported evidence and required checks, then use Matt Pocock conventions to perform exactly one requested action: local merge plus ticket update, PR creation plus ticket update, or ticket-only closure. State that decision/prototype evidence is valid completion evidence, a failed check does not close the ticket, and cleanup is opt-in. End with the `Area | Status | Detail` table schema for execute and finish responses.
